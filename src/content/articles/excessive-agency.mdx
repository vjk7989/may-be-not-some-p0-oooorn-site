# Excessive Agency: Applying Least Privilege to AI Agents

Excessive agency exists when an AI system has more functionality, permissions, or autonomy than its task requires. A customer-service agent that only needs to read order status should not be able to issue unlimited refunds, change account ownership, and send arbitrary external messages. Even if the model usually behaves well, broad authority increases the impact of mistakes, prompt injection, and compromised dependencies.

Least privilege gives an agent only the access it needs, for the time it needs, under the conditions its task requires. This does not prevent every bad decision. It limits the possible consequences and creates clear places to enforce policy.

## Break authority into four dimensions

Teams often describe an agent as having access to a tool, but tool access is only the beginning. Review authority across four dimensions:

1. **Functionality:** Which operations can the tool perform?
2. **Resources:** Which accounts, records, files, or environments can it affect?
3. **Magnitude:** What volume, value, or frequency is allowed?
4. **Autonomy:** Which actions can proceed automatically, and which need approval?

An agent may be allowed to draft a refund, for example, while a person must approve refunds above a threshold. It may read records for the requesting customer's account but not search across all customers.

## Replace generic tools with narrow capabilities

A broad shell, database, browser, or HTTP tool makes policy difficult to reason about. Prefer purpose-built operations with typed inputs: `getOrderStatus`, `draftRefund`, or `createSupportNote`. Validate each field and reject unknown parameters.

Keep read and write operations separate. A workflow that begins as research should not gain modification access for convenience. Buckleson's [AI security services](/services/) help teams map these execution boundaries and connect permissions to business impact.

The [OWASP description of excessive agency](https://genai.owasp.org/llmrisk/llm06-excessive-agency/) highlights excessive functionality, permissions, and autonomy as related sources of risk. The practical response is to reduce all three rather than relying on the model to self-restrain.

## Use identity that reflects the real actor

Do not run every agent under one powerful service account. Propagate the requesting user's identity and tenant context where possible. When a workload identity is necessary, give it a small scope and record which user or business process initiated the action.

Use short-lived credentials, restrict network destinations, and keep production permissions separate from development. Rotate or revoke access without redeploying the entire application. Never place reusable secrets in prompts, tool descriptions, or model-visible context.

## Put limits around magnitude and time

Authority should include bounds. Limit transactions per session, records per query, messages per hour, and financial value per action or day. Require a new decision when a request exceeds its approved scope.

Time limits matter too. A permission granted for one workflow should expire when the workflow ends. Long-running agents need periodic reauthorization, especially after model, tool, policy, or ownership changes.

Idempotency controls help prevent duplicated actions when a model retries after a timeout. For operations that cannot be made idempotent, expose the current state so the agent or reviewer can determine whether the action already completed.

## Add human approval where impact is high

Human review is most useful when it is specific. Show the proposed operation, real target, affected data, amount, destination, and expected effect. Do not ask someone to approve a vague statement such as “continue the task.” Bind the approval to the exact parameters and expire it if they change.

Use approvals for destructive actions, external communication, payments, access changes, regulated decisions, and other high-impact steps. A person should be able to deny, edit, or escalate the request. Track whether reviewers routinely approve without inspection; an approval step that receives no meaningful attention adds delay without much protection.

## Recheck policy immediately before execution

Planning and execution may be separated by seconds or hours. Permissions, data classification, and business state can change during that time. Evaluate policy again at the final boundary using the current actor, target, action, and context.

Fail safely if policy or identity services are unavailable. A silent fallback to broad access defeats the purpose of the gate. Return a clear status that allows an operator to retry or review without guessing which steps completed.

## Monitor sequences, not just individual calls

Each tool call may appear harmless while the sequence creates risk. An agent might read many small batches to bypass an export limit, probe identifiers, or combine data from separate sources. Correlate activity across the session and identity.

Watch for repeated denials, unusual tool order, rapid increases in volume, new destinations, approval churn, and attempts to invoke unavailable capabilities. Preserve sanitized evidence of the request, decision, approval, and result. ## Test authority as an attacker would

Build a permission matrix for roles, tools, resources, environments, and action levels. Test every denied cell, not only the expected allowed path. Include cross-tenant identifiers, stale permissions, malformed parameters, replayed approvals, duplicated requests, service failure, and indirect prompt injection.

Also test recovery. Can the team suspend one agent without stopping every AI feature? Can it revoke a credential, reverse a transaction, and identify affected records? The [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework) encourages ongoing measurement and management rather than treating launch approval as the final risk decision.

## Expand autonomy with evidence

Start new agents with read-only or draft-only capability. Measure failure rates, denial reasons, approval changes, and near misses. Expand scope one boundary at a time when the business value is clear and the controls have been tested. Reduce it again when the environment or evidence changes.

Least privilege makes AI autonomy more understandable. It helps limit blast radius, supports investigation, and gives organizations a disciplined path from assisted work to controlled execution. It is a continuing operating practice, not a one-time permission setting.
